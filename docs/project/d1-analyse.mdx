# D1 Analyse en toewijzing

Stand: 16 november 2026. Deze notitie is deliverable D1 van iteratie 1 van archiefwaardige opslag in Nextcloud, gefinancierd door het programma Common Ground van VNG.

## Samenvatting

We leggen de afdwinging van archiefregels zo laag mogelijk: in de opslaglaag, met Nextcloud Server als de plek die de uitkomst netjes aan de gebruiker toont. Een app kan zichzelf een bewaartermijn opleggen, maar een andere app of een beheerder kan daar omheen. Alleen een weigering in de opslaglaag houdt stand.

Wat we voorstellen:

- **Verzoek 4, bestuurde verwijdering.** Een Object Lock-bucket weigert de verwijdering. Nextcloud vertaalt die weigering naar een melding die de gebruiker begrijpt, en logt haar.
- **Verzoek 3, metagegevens.** Een integratie-app, [archiefmeta](https://github.com/ConductionNL/archiefmeta), toont de gegevens alleen-lezen in de Files-zijbalk, met bij elk gegeven de bron. Nextcloud bouwt de onderliggende schema-API (PR 66355) en laat de interface bewust aan integratie-apps over.
- **Verzoek 5, duurzame identiteit.** Elk record krijgt een identificatie die met het object meereist, ook over versies heen. Nextcloud werkt deze cyclus aan bestandsidentiteit op basis van hashes; wij stemmen daarop af.

De proof of concept heeft geen afhankelijkheid van een specifiek objectenregister. In de proof of concept is de opslaglaag de bron. Een objectenregister sluit later op dezelfde manier aan.

Verzoek 1, 2 en 6 wijzen we toe en beschrijven we. We bouwen ze niet in deze iteratie.

De voorstellen richting Nextcloud bouwen voort op de technische notitie *Records-management backend support in Nextcloud* van Erik Hoekstra (gemeente Haarlem), 19 augustus 2026.

## Huidige stand in Nextcloud

Nextcloud heeft bouwstenen voor alle drie verzoeken, maar geen ervan is af. Onderzocht op de broncode van `stable35` (35.0.1) en `master` (16 november 2026), op PR 66355, en met tests op MinIO met Object Lock.

| Onderwerp | Wat er is | Wat ontbreekt |
| --- | --- | --- |
| Metagegevens | Getypeerde waarden per bestand sinds Nextcloud 28 (`IFilesMetadataManager`). Zichtbaar via WebDAV als `nc:metadata-<sleutel>`. Een veld kan op "niemand mag wijzigen" staan (`EDIT_FORBIDDEN`). | Geen bron per waarde. "Niemand mag wijzigen" geldt alleen voor WebDAV, niet voor code in de server. Een geweigerde wijziging geeft HTTP 500 in plaats van 403 ([#43351](https://github.com/nextcloud/server/issues/43351)). Geen weergave in Files. |
| Retentie | [`files_retention`](https://github.com/nextcloud/files_retention) verwijdert bestanden met een tag na een termijn. Prullenbak en versies verlopen op eigen instellingen. | Niets dat een verwijdering weigert met een reden. `files_retention` beschermt niets: een gebruiker kan een getagd bestand op elk moment zelf verwijderen. |
| Verwijderen op S3 | Nextcloud stuurt een gewone delete zonder versie, bij primaire objectopslag en bij externe S3-opslag. | Geen ondersteuning voor Object Lock. Getest: op een bucket met Object Lock meldt Nextcloud een geslaagde verwijdering, terwijl de bytes blijven staan. Zie [de testresultaten](../evidence/s3-object-lock-deletes.md). |
| Objectidentiteit | Het `fileid` blijft gelijk bij hernoemen en verplaatsen, ook naar andere opslag. Links werken via `/f/<fileid>`. | Een identificatie per record over versies heen ontbreekt. Getest: weigert de opslag het verwijderen van een map, dan krijgen de bestanden na een herscan nieuwe `fileid`'s. |
| Schema-API (PR 66355) | Apps registreren getypeerde velden (tekst, getal, datum, keuzelijst) en bepalen per bestand en gebruiker wie mag lezen en wijzigen. Gericht op Nextcloud 36. | Geen lijsttype, geen interface. Bron per waarde hoort volgens Nextcloud in de auditlog, niet in de metagegevens. |

| Verzoek | Component | Benodigde interface | Status bij Nextcloud | Deze iteratie |
| --- | --- | --- | --- | --- |
| 1. Wijzigingsmeldingen uit de opslaglaag | Server, opslaglaag | Een kanaal waarlangs de opslag wijzigingen meldt, zodat de bestandsindex bijloopt zonder volledige scan | Core kent `INotifyStorage` al voor SMB; geen voorstel voor S3 | Analyse |
| 2. Gedelegeerde versiegeschiedenis | Server (`files_versions`), opslaglaag | Versiebeheer van de opslag als versiebron | Versiebronnen (`IVersionBackend`) bestaan; geen voorstel voor S3 | Analyse |
| 3. Metagegevens uit de opslaglaag, alleen-lezen | Server (schema-API), integratie-app, opslaglaag | Getypeerde velden met wijzigrecht in core; weergave met bron in een app | [PR 66355](https://github.com/nextcloud/server/pull/66355) open (Nextcloud 36) | **D3**, als app |
| 4. Bestuurde verwijdering | Opslaglaag, Server, objectenregister | Een getypeerde weigering met reden en een gebeurtenis voor logging; Object Lock-bewust verwijderen op S3 | [Issue 66498](https://github.com/nextcloud/server/issues/66498) open | **D2** |
| 5. Duurzame objectidentiteit | Server, opslaglaag | Een identificatie per record, oplosbaar naar de actuele locatie | [Issue 66499](https://github.com/nextcloud/server/issues/66499) open; Nextcloud werkt aan hash-identiteit | **D5** |

Verzoek 5 is de basis onder de rest. Een melding, een versie, een logregel en een metagegeven wijzen allemaal een object aan.

## Besluitvoorstel: vier architectuurkeuzes

| Keuze | Voorstel | Hoe we het waarmaken |
| --- | --- | --- |
| (a) De opslaglaag kan een verwijdering weigeren, niet alleen een app | Overnemen | De S3-bucket draait met Object Lock. Core herkent de weigering en geeft haar door met reden. Geen app kan haar omzeilen. |
| (b) Het objectenregister is de enige bron van de bewaartermijn | Overnemen als principe | In productie is het objectenregister de bron. In de proof of concept is het de opslaglaag zelf: de vergrendeldatum op het object. Zo werkt het resultaat ook zonder register. |
| (c) Metagegevens dragen bronvermelding | Overnemen | Elke waarde draagt een bron en een tijdstip. De Files-zijbalk toont ze naast het gegeven. |
| (d) Archiefwet-functionaliteit werkt zonder SLA-abonnement | Overnemen | Alles wat wij bouwen is AGPL-3.0, zonder licentiesleutel of activatie. |

**Keuze (a) staat onder druk.** Nextcloud gaf aan dat verwijderen loopt via Nextcloud Governance, in de permissielaag, en dat de opslag geen bedrijfsregels hoeft te kennen. Dat is het risico dat de opdracht noemt: verzoek 4 wordt app-retentie. Het besluit ligt bij opdrachtgever en Product Owner. Daarbij weegt mee dat de Governance-app niet openbaar is, en dat nog onbekend is of ze werkt zonder abonnement (keuze d).

## App-retentie versus weigering door de opslaglaag

App-retentie is een afspraak, een weigering door de opslaglaag is een slot.

| | App-retentie | Weigering door de opslaglaag |
| --- | --- | --- |
| Wie beslist | Een Nextcloud-app, via een gebeurtenis of een opslagfilter | De opslag zelf, met Object Lock |
| Wie kan eromheen | Een beheerder die de app uitzet, code die buiten de app om schrijft, rechtstreekse toegang tot de bucket | Niemand vóór de vergrendeldatum, in compliance-modus ook de beheerder van de opslag niet |
| Werkt zonder Nextcloud | Nee | Ja |
| Wat de gebruiker nu ziet | Een kale 403, of een verwijdering die lijkt te lukken | Op S3 vandaag: een verwijdering die lijkt te lukken |
| Wat de gebruiker straks ziet | Dezelfde melding als bij de opslaglaag, met reden | "Dit document valt onder een bewaartermijn tot 1 maart 2031 en kan niet worden verwijderd." |

We houden beide. App-retentie blijft nuttig als eerste filter. Voor archiefwaardige objecten is alleen de opslaglaag genoeg. Core moet dan twee dingen doen: de weigering herkennen en haar netjes doorgeven.

## Overlap met bestaande apps

Bestaande apps voor metagegevens en dossierbeheer op Nextcloud beschrijven archiefgegevens, maar dwingen niets af. We hebben twee van zulke apps onderzocht als functionele input; deze iteratie gebruikt geen van beide.

| Functie | Gezien in de markt | Plek in dit traject |
| --- | --- | --- |
| Getypeerde velden, keuzelijsten, standaardwaarden | Ja | Schema-API (PR 66355) |
| Veldschema per map of dossiertype | Ja | Vervolgverzoek |
| Metagegevens als kolom in Files, zoeken erop | Ja, via eigen zoekindex | Zijbalk in D3; kolommen en zoeken als vervolgverzoek |
| Sjablonen voor Archiefwet, Woo en AVG | Ja, beschrijvend | MDTO-velden in D3 |
| Verwijdering weigeren, legal hold | Nee | D2 |
| Bronvermelding per gegeven | Nee | D3 |
| Duurzame identiteit los van locatie | Nee | D5 |
| MDTO-export, e-depot, vernietigingsbesluit | Nee | Archief-app, buiten deze iteratie |

## Uitwerking per deliverable

1. **D3, metagegevens.** De app [archiefmeta](https://github.com/ConductionNL/archiefmeta) leest classificatie, bewaartermijn, zorgdrager en identificatie uit de opslag en slaat ze op via de metadata-API van Nextcloud, met `EDIT_FORBIDDEN`. Zodra de schema-API uit PR 66355 er is, stappen we over.
2. **D2, verwijdering.** Eerst de S3-fout: Nextcloud moet een weigering van de opslag herkennen in plaats van succes te melden. Wachten op de reactie van Nextcloud op issue 66498 en op het besluit over keuze (a). Scenario B, verwijderen na een vernietigingsbesluit, vraagt governance-modus met een apart opslagaccount.
3. **D5, identiteit.** Afstemmen op de hash-identiteit van Nextcloud. Ons verzoek: een identificatie per record die gelijk blijft over versies heen, naast een hash per versie.

**Opstelling.** MinIO met Object Lock en Nextcloud in een geïsoleerde testomgeving, zonder productiedata en zonder persoonsgegevens.
