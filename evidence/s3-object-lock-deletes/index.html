S3 Object Lock deletes

Evidence for nextcloud/server#66498: what Nextcloud does when the storage layer should refuse a delete. Tested on 16 November 2026 against Nextcloud 34.0.0.12 with MinIO. The delete paths are identical on Nextcloud master of the same day (see the last section).

Summary​

ScenarioStorageWhat Nextcloud answersWhat happens to the bytesLogged
A.1Primary storage, locked bucket, trash bin on204, file in the trash binObject untouchedNothing
A.2Same file, purged from the trash bin204, file gone from NextcloudDelete marker; locked version stays readable by version IDNothing
A.3Primary storage, locked bucket, trash bin off204, then 404 on GETDelete marker; locked version staysNothing
BExternal S3 mount, locked bucket204, file in the trash binDelete marker on the external bucket; a second copy is written to primary storage for the trash binNothing
CExternal locked bucket, folder of three files204Delete marker per file; all versions stayNothing
DExternal locked bucket, legal hold on204Delete marker; the version under legal hold staysNothing
E (control)External bucket without versioning or lock204Objects really deletedNothing
FExternal bucket, policy denies s3:DeleteObject403 with an empty message, file and folder stayUntouchedError per attempt
GExternal bucket, policy denies deletes inside the folder only204Untouched; the folder and files reappear in Nextcloud with new file IDsOnly "trash move failed" with the trash bin on, nothing with it off

In short: Nextcloud sends deletes without a version ID. On a bucket with Object Lock that creates a delete marker. Nextcloud reports success and removes the file from its index, while the locked bytes stay in the bucket. Deleting the locked version itself is refused by the storage (last sections). A refusal that does reach Nextcloud shows as a bare 403 without a reason.
